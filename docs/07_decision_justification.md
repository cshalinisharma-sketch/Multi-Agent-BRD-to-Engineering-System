# 7. Decision Justification

| Decision | Choice | Alternatives considered | Why |
|---|---|---|---|
| Tool track | Python (code track) with **LangGraph** orchestration + pydantic contracts | n8n/Langflow (low-code); CrewAI; plain Python loop | LangGraph gives an explicit, inspectable graph (conditional Critic loop with a cap, `interrupt()` for the HITL gate, checkpoints, LangSmith tracing) while agents stay plain `state → artifact` classes testable without the framework. The plain loop is kept as `--engine classic` and produces identical outputs. |
| Orchestration pattern | Hub-and-spoke with a bounded Critic→agent revision edge | Sequential pipeline, hierarchical, message graph | See `01_architecture.md §1.3`: central state + validation + selective re-runs, easiest to explain and log; the only loop we need is bounded at 2. |
| Output contracts | pydantic v2 models + exported JSON Schema | free-form JSON, TypedDicts | Validation with field-level errors that can be fed back to an LLM; cross-field validators (milestones reference phases, flows reference components); schemas double as documentation. |
| LLM provider | OpenAI or Anthropic through **LangChain** chat models (`ChatOpenAI`, `ChatAnthropic`); plain-HTTPS fallback; offline deterministic engine | single vendor SDK; raw HTTP only | One interface for both providers, token usage for cost tracking, automatic LangSmith tracing; provider switch by flag or env var. The offline engine makes the system reproducible, testable in CI, and is the fallback after repeated contract violations. Online use is opt-in behind a data-boundary confirmation. |
| Model routing | small model: Orchestrator, Schedule, PoC, Critic judge · large model: Plan, Architecture, Tech stack, eval judge | one model for everything | Routing/classification and arithmetic-heavy steps don't need the large model; design reasoning does. Cuts expected cost roughly in half for the same quality on reasoning steps. |
| Embeddings | Local LSA (TF-IDF → SVD) fused with sparse TF-IDF | OpenAI `text-embedding-3-small`, sentence-transformers | 78-chunk domain corpus; hybrid keeps exact tech/ID terms; $0, deterministic, offline. OpenAI embedder included for larger corpora. |
| Vector DB | In-process numpy store with Chroma-like interface + metadata filters | Chroma, FAISS, Qdrant, Pinecone | < 1k chunks, no infrastructure, reproducible. Swap to Qdrant/pgvector at the 50+ BRDs/week scale (see `01 §1.7`). |
| Chunking | Heading-path sections (narrative), one-per-pattern, one-per-row (tables) | fixed-size token windows | Matches the natural semantic units; keeps structured lines parseable; see `03_rag_design.md`. |
| Retrieval profile | tuned: top-k 5, hybrid, per-agent filters | baseline: top-k 2, dense, no filters | Measured: round-0 groundedness 82.5% → 93.3%, Critic issues −45% (`04 §4.5`). |
| Critic design | Rule-scored dimensions + heuristic/LLM actionability + 10 cross-agent checks + grounding guardrails | pure LLM-as-judge critic | Deterministic checks for what is checkable (coverage, citations, consistency) are cheaper and more reliable than asking an LLM; the LLM is reserved for the subjective dimension (actionability). Calibrated against reference scores (MAE 0.44). |
| Revision cap | 2 rounds, fix memory, dependent cascade | unbounded loop; single-shot | Brief requirement; prevents loops; fix memory stops regressions when an agent is re-run as a dependent. |
| Schedule method | Analog-based (effort per requirement from the most relevant past projects; p80 from historical variance) | LLM guess; story points | Grounded, explainable, and honest about uncertainty; analogs are cited so the EM can challenge them. |
| Pattern choice | Score all patterns: retrieval + explicit signal matching + hard constraints | top-1 retrieval | Retrieval alone misclassified a dispute portal as search-centric during development; explicit signals and constraints (on-prem, team size, real-time) fix that and are explainable in the rationale. |
| Tech-stack scoring | Weighted (scalability, familiarity, integration risk, cost) with weights shifted by NFRs; familiarity from the org matrix, risk from past decision outcomes | expert rules only | Makes trade-offs explicit and reproducible; correctly rejects Flink (familiarity 1, TD-05 failure) and DynamoDB for relational audit workloads. |
| Exports | Markdown + PDF + Jira (mock REST client) + HTML dashboard | Confluence/Jira live integration | Mock client mirrors Jira's REST shape so swapping to the real API is a single class; avoids credentials in a capstone repo. |
| Stretch | MCP server (parse + retrieve tools), HTML EM dashboard, Jira epics/stories export | voice, fine-tuning | Highest leverage for an EM workflow; voice and fine-tuning need API access/compute not available in the build environment. |
| Build vs buy | Build the agents, knowledge base and rubric; buy the model (API) and use open frameworks (LangGraph / LangChain) | buy an AI planning tool; train or host our own LLM | Our differentiator is our history, standards and rubric, not the model. A bought API gives time to market; open frameworks avoid vendor lock-in and keep the provider swappable. |
| Fine-tuning | Not used; optimise with retrieval tuning, prompts, model routing and the Critic loop | fine-tune a model on past plans | ~12 past projects are far too few to fine-tune; RAG keeps answers current when the knowledge base changes and every claim citable. Revisit when hundreds of approved packs exist. |
| Prompt design | One Agent Prompt Template for every agent: ROLE, SCOPE, FORMAT, CONSTRAINTS, COMMAND, TOOL GUIDANCE, OUTPUT STRUCTURE, TONE + shared rules | free-form prompts per agent | Consistent, reviewable prompts; the output structure names the exact contract fields (`src/prompts.py`). |
| Evaluation frameworks | scikit-learn classification metrics for Critic calibration; LangSmith for tracing; own rule checks, ROUGE-L and LLM-as-Judge | RAGAS / DeepEval only | Critic verdicts are a binary classification problem, so precision / recall / F1 / kappa are the honest numbers; LLM-based eval frameworks need a key and would make the offline gates non-reproducible. |
| Caching | Opt-in on-disk response cache keyed by provider, model and full prompt | no cache; LangChain in-memory cache | Re-runs and evals of the same input cost no tokens; in-memory caches don't survive across runs. Opt-in because cached text is BRD-derived. |
